## เป้าหมายคอร์ส

ผู้เรียนสามารถใช้ AI ช่วยพัฒนาซอฟต์แวร์อย่างเป็นระบบ ตั้งแต่เลือกเทคโนโลยี ตั้งค่าโปรเจกต์ เขียน Spec และ Plan พัฒนาแบบ TDD ตรวจความปลอดภัย จนส่งมอบ MVP ที่ใช้งานได้จริงบน Git repository

## ผลลัพธ์หลังเรียน

ผู้เรียนจะสามารถ:

- เลือก Tech Stack ให้เหมาะกับปัญหา ไม่เลือกเพราะกระแส
    
- เริ่มโปรเจกต์ด้วยโครงสร้างมาตรฐานและทำงานร่วมกับ AI ได้ดี
    
- เขียน Spec, Plan และแบ่งงานก่อนเริ่มเขียนโค้ด
    
- ใช้ AI เป็น pair programmer โดยยังคงตรวจสอบผลลัพธ์เอง
    
- เขียนและใช้ Test เพื่อควบคุมคุณภาพโค้ด
    
- ป้องกันการเผลอส่ง Secret ขึ้น Git
    
- สร้าง MVP ที่เล็กพอ ส่งมอบได้ และต่อยอดได้จริง

# Module 1: Mindset ของ AI Coding ที่ดี

AI ไม่ใช่คนที่ “รับคำสั่งแล้วเขียนทุกอย่างให้” แต่เป็นผู้ช่วยพัฒนา ที่ต้องมีบริบท ข้อจำกัด และเกณฑ์ตรวจรับที่ชัดเจน

หลักคิดสำคัญ:

- AI เขียนเร็ว แต่ไม่ได้แปลว่าถูกเสมอ
    
- อย่าเชื่อโค้ดที่ยังไม่ได้รันและทดสอบ
    
- ให้ AI ทำงานเป็นรอบเล็ก ๆ: เข้าใจ → วางแผน → เขียน → ทดสอบ → Review
    
- ทุกครั้งต้องรู้ว่า “เรากำลังแก้ปัญหาอะไร” ไม่ใช่เพียง “กำลังเขียนไฟล์อะไร”
    
- อย่าใส่ Secret, ข้อมูลผู้ป่วย, ข้อมูลลูกค้า หรือข้อมูลส่วนบุคคลลงใน Prompt โดยไม่จำเป็น
    

แบบฝึกหัด: เปรียบเทียบ Prompt ที่คลุมเครือกับ Prompt ที่ระบุเป้าหมาย ขอบเขต และเกณฑ์ผ่านงานชัดเจน

# Module 2: Choose Tech — เลือกเทคโนโลยีอย่างมีเหตุผล

ก่อนเลือก Framework ให้ตอบคำถามเหล่านี้ก่อน:

1. ผู้ใช้คือใคร และต้องทำงานอะไรให้สำเร็จ
    
2. เป็น Web, Mobile, API, Dashboard หรือ Automation
    
3. ต้องมี Login, Role, Database, File Upload หรือ Notification หรือไม่
    
4. ทีมมีความรู้เทคโนโลยีใดอยู่แล้ว
    
5. ต้อง Deploy ที่ไหน งบประมาณเท่าไร
    
6. ข้อมูลมีความสำคัญหรือมีข้อกำหนดด้านความปลอดภัยหรือไม่
    
7. ระบบต้องรองรับผู้ใช้มากน้อยเพียงใด
    

ตัวอย่างแนวทางเลือก:

| โจทย์                         | ตัวเลือกที่เหมาะสม                                       |
| ----------------------------- | -------------------------------------------------------- |
| Landing page / เว็บไซต์องค์กร | Next.js, Astro, SvelteKit                                |
| ระบบหลังบ้าน / Dashboard      | Next.js หรือ SvelteKit + PostgreSQL                      |
| Mobile app                    | React Native / Flutter                                   |
| API อย่างเดียว                | Node.js, FastAPI, Go                                     |
| Prototype ที่ต้องออกเร็ว      | Supabase + Next.js / SvelteKit                           |
| ระบบข้อมูลสำคัญ               | Backend ที่มี RBAC, Audit log, Database backup และ CI/CD |

หลักเลือกเทคโนโลยี:

- เลือกสิ่งที่ทีมดูแลต่อได้
    
- เริ่มจาก Stack ที่เรียบง่ายก่อน
    
- หลีกเลี่ยงการเพิ่มเครื่องมือโดยไม่มีเหตุผล
    
- แยก “ของจำเป็นสำหรับ MVP” ออกจาก “ของที่น่าสนใจแต่ยังไม่จำเป็น”
    

แบบฝึกหัด: เลือก Tech Stack สำหรับระบบจองคิวขนาดเล็ก พร้อมอธิบายเหตุผล

# Module 3: Config Project — ตั้งค่าโปรเจกต์ให้พร้อมทำงาน

สิ่งที่ควรมีตั้งแต่วันแรก:

- README.md: โปรเจกต์นี้คืออะไร, วิธีรัน, วิธีทดสอบ
    
- `.gitignore`: ป้องกันไฟล์ที่ไม่ควรขึ้น Git
    
- `.env.example`: ตัวอย่างตัวแปรแวดล้อมโดยไม่มี Secret
    
- Formatter: เช่น Prettier
    
- Linter: เช่น ESLint
    
- Test framework: เช่น Vitest, Jest หรือ Playwright
    
- CI: รัน lint, test และ build ทุกครั้งก่อน merge
    
- Dependency lock file: เช่น `pnpm-lock.yaml`
    

ตัวอย่างคำสั่งเริ่มต้น:

```
git init
git add .
git commit -m "chore: initialize project"
```

สิ่งที่ไม่ควร Commit:

```
node_modules/
.env
.env.local
dist/
build/
coverage/
.DS_Store
```

แนวทางจัดการ Environment Variables:

- เก็บ Secret ไว้ใน `.env` เท่านั้น
    
- Commit เฉพาะ `.env.example`
    
- แยกค่า Development, Staging และ Production
    
- ห้าม hardcode API key, password หรือ token ใน source code
    

แบบฝึกหัด: สร้าง repository ใหม่ พร้อม README, `.gitignore`, `.env.example` และ commit แรก

# Module 4: ตั้งค่า AI Coding Context — AGENTS.md และ CLAUDE.md

AI ทำงานได้ดีขึ้นมากเมื่อรู้กติกาของโปรเจกต์

ไฟล์ที่แนะนำ:

- `AGENTS.md`: กติกาสำหรับ AI agent ที่เข้ามาทำงานในโปรเจกต์
    
- `CLAUDE.md`: บริบท คำสั่ง และมาตรฐานเฉพาะสำหรับ Claude หรือ AI assistant ที่ใช้
    
- `README.md`: คู่มือสำหรับคนในทีม
    

เนื้อหาที่ควรใส่ใน `AGENTS.md`:

- วิธีติดตั้งและรันโปรเจกต์
    
- คำสั่ง lint, test และ build
    
- โครงสร้างโฟลเดอร์
    
- Coding conventions
    
- แนวทางตั้งชื่อไฟล์และ commit
    
- **ข้อห้าม เช่น ห้ามแก้ schema โดยไม่สร้าง migration**
    
- นโยบายข้อมูลสำคัญและ Secret
    
- Definition of Done ของงาน
    

ตัวอย่าง Definition of Done:

- ฟีเจอร์ตรงตาม Spec
    
- มี Test ในส่วนสำคัญ
    
- Lint ผ่าน
    
- Build ผ่าน
    
- ไม่มี Secret ใน Git
    
- README หรือเอกสารถูกอัปเดตเมื่อจำเป็น
    
- Reviewer อ่านและเข้าใจการเปลี่ยนแปลงได้
    

แบบฝึกหัด: เขียน `AGENTS.md` สำหรับโปรเจกต์ MVP ของตนเอง

# Module 6: เขียน Spec ก่อน Coding

Spec คือเอกสารที่บอกว่า “ต้องสร้างอะไร” ไม่ใช่บอกว่า “จะเขียนโค้ดอย่างไร”

โครงสร้าง Spec ที่ดี:

```
# Feature: ระบบจองคิว

## Problem
ผู้ใช้ต้องโทรศัพท์เพื่อจองคิว ทำให้เสียเวลาและติดตามยาก

## Goal
ให้ผู้ใช้เลือกวัน เวลา และยืนยันการจองผ่านเว็บไซต์ได้

## Users
- ผู้รับบริการ
- เจ้าหน้าที่

## User Stories
- ผู้ใช้เลือกวันและเวลาที่ว่างได้
- ผู้ใช้ยืนยันการจองได้
- เจ้าหน้าที่ดูรายการจองได้

## Acceptance Criteria
- ไม่สามารถจองช่วงเวลาที่เต็มแล้วได้
- ผู้ใช้ได้รับเลขอ้างอิงหลังจองสำเร็จ
- เจ้าหน้าที่เห็นรายการจองตามวันที่เลือกได้

## Out of Scope
- ชำระเงินออนไลน์
- การแจ้งเตือนผ่าน LINE
- การเลื่อนนัดอัตโนมัติ
```

ข้อผิดพลาดที่พบบ่อย:

- เขียนว่า “ทำระบบจองคิว” แต่ไม่มีเงื่อนไขการจอง
    
- ไม่มีการระบุว่าใครใช้งาน
    
- ไม่มีเกณฑ์ที่บอกว่างานเสร็จหรือยัง
    
- ใส่ฟีเจอร์มากเกินไปจน MVP ส่งไม่ทัน

# Module 7: เขียน Plan ก่อน Coding

Plan คือเอกสารที่บอกว่า “จะทำอย่างไรเป็นลำดับ”

ตัวอย่าง Plan:

```
1. สร้างโครงสร้างฐานข้อมูลสำหรับตาราง appointments
2. สร้าง API สำหรับอ่านช่วงเวลาว่าง
3. สร้าง API สำหรับสร้างการจอง
4. ป้องกันการจองเวลาซ้ำในระดับฐานข้อมูล
5. สร้างหน้าฟอร์มเลือกวันและเวลา
6. สร้างหน้าสรุปผลการจอง
7. เขียน unit test สำหรับกฎการจอง
8. เขียน end-to-end test สำหรับ flow การจอง
9. รัน lint, test และ build ก่อนส่งงาน
```

หลักการเขียน Plan:

- แต่ละข้อควรเล็กพอที่จะตรวจสอบได้
    
- ระบุไฟล์หรือส่วนที่เกี่ยวข้องเมื่อทำได้
    
- ระบุความเสี่ยง เช่น การจองพร้อมกันหลายคน
    
- แยกงานที่ต้องตัดสินใจออกจากงานที่ทำตามแบบได้
    
- อย่าให้ AI เปลี่ยนหลายเรื่องในครั้งเดียว

# Module 8.0: UI/UX สำหรับ AI Coding และ CSS Framework

เป้าหมายของ UI/UX ไม่ใช่ทำให้หน้าจอสวยอย่างเดียว แต่ทำให้ผู้ใช้ทำงานสำเร็จได้เร็ว ผิดพลาดน้อย และเข้าใจสถานะของระบบ

## หลัก UI/UX ที่ควรสอน

ก่อนเริ่มสร้างหน้า UI ให้ตอบคำถาม:

- ผู้ใช้คือใคร
- ผู้ใช้เข้ามาทำงานอะไรเป็นหลัก
- Flow ที่สำคัญที่สุดคืออะไร
- ผู้ใช้ต้องตัดสินใจอะไรบ้างในแต่ละหน้า
- จุดไหนที่ผู้ใช้อาจสับสนหรือกรอกข้อมูลผิด
- หลังจากกดปุ่มแล้ว ระบบควรแสดงสถานะอะไร

หลักพื้นฐาน:

- หนึ่งหน้าควรมีเป้าหมายหลักที่ชัดเจน
- ให้ความสำคัญกับ Flow การใช้งานก่อนความสวยงาม
- ใช้ข้อความบนปุ่มให้บอกการกระทำชัดเจน เช่น “บันทึกการจอง” แทน “ตกลง”
- แสดง Loading, Success, Empty และ Error states เสมอ
- ฟอร์มต้องบอกข้อมูลที่จำเป็น และแสดง validation ใกล้ช่องที่ผิด
- อย่าพึ่งพาสีเพียงอย่างเดียวในการสื่อความหมาย
- รองรับหน้าจอมือถือ และใช้งานด้วยคีย์บอร์ดได้
- ใช้ spacing, สี, typography และรูปแบบปุ่มอย่างสม่ำเสมอ

## ออกแบบก่อนให้ AI เขียน UI

Prompt ที่ดีควรระบุ:

```text
สร้างหน้าจองคิวสำหรับผู้รับบริการ

ผู้ใช้ต้องเลือกวันที่ เลือกช่วงเวลา กรอกชื่อและเบอร์โทรศัพท์
ต้องแสดงช่วงเวลาที่เต็มเป็น disabled
ต้องมี loading state ระหว่างบันทึก
ต้องแสดง error ใต้ field เมื่อกรอกข้อมูลไม่ถูกต้อง
เมื่อสำเร็จ ให้แสดงเลขอ้างอิงการจอง
รองรับ mobile-first และ accessibility พื้นฐาน
ใช้ component จาก shadcn/ui และ Tailwind CSS
```

ห้ามสั่งเพียงว่า:

```text
สร้างหน้าจองคิวให้สวย ๆ
```

เพราะ AI อาจได้หน้าจอที่ดูดี แต่ไม่ตรงกับ flow การทำงานจริง

## CSS Framework และ Component Library

การใช้ CSS Framework ช่วยให้ MVP ออกแบบและพัฒนาได้เร็วขึ้น มีมาตรฐาน และลดการเขียน CSS ซ้ำ

เลือกใช้ให้เหมาะกับ Stack และทีม

| เครื่องมือ        | เหมาะกับ                             | จุดเด่น                                           | ข้อควรระวัง                                        |
| ----------------- | ------------------------------------ | ------------------------------------------------- | -------------------------------------------------- |
| Tailwind CSS      | ทีมที่ต้องการควบคุมดีไซน์เอง         | ยืดหยุ่น, ทำ UI เร็ว, ปรับแต่งง่าย                | class ใน HTML อาจยาว ต้องมีมาตรฐาน                 |
| shadcn/ui         | Next.js / React + Tailwind           | Component สวย, แก้ source ได้, เหมาะกับ dashboard | ต้องเข้าใจ Tailwind และดูแล component ที่นำเข้าเอง |
| Material UI (MUI) | ระบบองค์กร, Dashboard, ฟอร์มจำนวนมาก | Component ครบ, accessibility ดี, เริ่มเร็ว        | หน้าตาอาจคล้าย Material หากไม่ปรับ theme           |
| Ant Design        | ระบบหลังบ้านและตารางข้อมูล           | Table, Form, Date picker ครบ                      | น้ำหนัก bundle และรูปแบบเฉพาะตัว                   |
| Bootstrap         | ผู้เริ่มต้นหรือระบบ legacy           | เรียนง่าย, เอกสารเยอะ                             | ถ้าไม่ปรับแต่ง หน้าตามักเหมือนกัน                  |
| DaisyUI           | Tailwind MVP ที่ต้องออกเร็ว          | ใช้งานง่าย มี theme สำเร็จรูป                     | ความยืดหยุ่นและความละเอียดน้อยกว่า shadcn/ui       |

## คำแนะนำการเลือก

- ใช้ **shadcn/ui + Tailwind CSS** สำหรับ React หรือ Next.js ที่อยากได้ UI สะอาด ปรับแต่งได้ และไม่เหมือนเว็บสำเร็จรูป
- ใช้ **Material UI** สำหรับระบบองค์กรที่มีฟอร์ม ตาราง เมนู และหน้าจอจัดการข้อมูลจำนวนมาก
- ใช้ **Ant Design** เมื่อต้องทำ Admin dashboard หรือ data-heavy application อย่างรวดเร็ว
- ใช้ **Bootstrap** เมื่อทีมเริ่มต้นหรือมีระบบเดิมที่ใช้อยู่แล้ว

กฎสำคัญ:

> เลือก Component Library เพียงหนึ่งชุดเป็นหลักต่อหนึ่งโปรเจกต์  
> ไม่ควรผสม shadcn/ui, Material UI, Ant Design และ Bootstrap ในหน้าจอเดียวกัน

## Design System ขนาดเล็กสำหรับ MVP

ก่อนเริ่มทำหลายหน้า ให้กำหนดมาตรฐานขั้นต่ำ:

- สีหลัก 1 สี, สีสถานะ success/warning/error
- ขนาดข้อความสำหรับ title, heading, body, helper text
- ระยะห่างมาตรฐาน เช่น 4, 8, 12, 16, 24, 32 px
- รูปแบบปุ่มหลัก, ปุ่มรอง และปุ่มอันตราย
- รูปแบบ input, select, date picker และ error message
- รูปแบบตาราง, empty state และ loading state

ตัวอย่าง Component ขั้นต่ำของระบบหลังบ้าน:

```text
Button
Input
Select
Textarea
Checkbox
Dialog / Confirmation dialog
Toast
Table
Pagination
Badge / Status
Skeleton / Loading

Error state
```

## UI States ที่ต้องมี

ทุก feature ที่เกี่ยวข้องกับข้อมูลควรพิจารณาอย่างน้อย:

```text
Default
Loading
Empty
Success
Validation error
System error
Permission denied
```

ตัวอย่างหน้ารายการจอง:

- Loading: แสดง skeleton table
- Empty: “ยังไม่มีรายการจองในวันนี้” พร้อมปุ่มสร้างรายการ
- Error: บอกปัญหาและปุ่มลองใหม่
- Permission denied: บอกว่าไม่มีสิทธิ์เข้าถึง ไม่แสดงข้อมูลส่วนเกิน

## Accessibility Checklist

- ทุก input มี label
- ปุ่มมีข้อความหรือ aria-label ที่สื่อความหมาย
- สีตัวอักษรตัดกับพื้นหลังเพียงพอ
- ใช้ Tab เพื่อไปยังปุ่มและฟอร์มได้
- Dialog สามารถปิดและ focus กลับตำแหน่งเดิมได้
- Error message อ่านได้ด้วย screen reader
- อย่าใช้ placeholder แทน label

## แบบฝึกหัด

1. User flow แบบสั้น
2. Wireframe หรือรายการ component ที่ใช้
3. Loading, Empty, Error และ Success state
4. เลือก CSS Framework หรือ Component Library พร้อมเหตุผล
5. Prompt ให้ AI สร้าง UI โดยระบุ requirement ที่ตรวจสอบได้
6. ตรวจ UI บนมือถือและ Desktop ก่อนส่งงาน
# Module 9: การสร้าง MVP

MVP คือผลิตภัณฑ์เวอร์ชันเล็กที่สุดที่พิสูจน์ว่าปัญหานั้นควรแก้ และผู้ใช้ได้รับคุณค่า

สูตรคิด MVP:

```
ปัญหาหลัก 1 เรื่อง
+ ผู้ใช้หลัก 1 กลุ่ม
+ งานสำคัญ 1 Flow
= MVP ที่ควรเริ่มทำ
```

ตัวอย่างระบบจองคิว:

MVP:

- เลือกวัน
    
- เลือกเวลาว่าง
    
- กรอกชื่อและเบอร์โทรศัพท์
    
- ยืนยันการจอง
    
- เจ้าหน้าที่ดูรายการจองได้
    

ยังไม่ต้องมี:

- ระบบสะสมแต้ม
    
- หลายสาขา
    
- Payment gateway
    
- LINE chatbot
    
- Dashboard ที่มีกราฟจำนวนมาก
    
- ระบบ recommendation
    

หลักการสำคัญ:

- สร้าง Flow หลักให้จบก่อน
    
- เริ่มจากข้อมูลจริงที่จำเป็น
    
- วัดผลจากการใช้งาน ไม่ใช่จำนวนฟีเจอร์
    
- เก็บ Feedback ก่อนขยายระบบ
    

แบบฝึกหัด: ลดไอเดียระบบของผู้เรียนให้เหลือ MVP ที่ทำเสร็จได้ภายใน 1–2 สัปดาห์

# Module 10: TDD — Test-Driven Development

TDD คือแนวทางที่เขียน Test ก่อน แล้วเขียน Production Code ให้ Test ผ่าน

วงจร TDD:

```
Red → Green → Refactor
```

- Red: เขียน Test แล้วให้ Test ล้มเหลวก่อน
    
- Green: เขียนโค้ดขั้นต่ำเพื่อให้ Test ผ่าน
    
- Refactor: ปรับโค้ดให้สะอาด โดย Test ยังผ่านทั้งหมด
    

ตัวอย่างกรณีที่ควรมี Test:

- กฎธุรกิจ เช่น ส่วนลด, คะแนน, สิทธิ์การเข้าถึง
    
- การตรวจข้อมูลก่อนบันทึก
    
- การคำนวณ
    
- การป้องกันข้อมูลซ้ำ
    
- Permission และ Role
    
- API ที่มีผลต่อข้อมูลสำคัญ
    

ตัวอย่าง Test Case ระบบจองคิว:

- จองเวลาว่างได้
    
- จองเวลาที่ถูกจองแล้วไม่ได้
    
- วันเวลาที่ผ่านมาแล้วจองไม่ได้
    
- ข้อมูลไม่ครบไม่สามารถจองได้
    
- ผู้ใช้ที่ไม่มีสิทธิ์ไม่สามารถดูข้อมูลผู้อื่นได้
    

ข้อควรระวัง:

- ไม่จำเป็นต้อง TDD ทุก CSS หรือทุกข้อความบนหน้าเว็บ
    
- ให้ TDD กับ logic สำคัญก่อน
    
- Test ที่ดีต้องอ่านแล้วรู้พฤติกรรมของระบบ

# Module 11: Git Workflow และ Code Review

แนวทางทำงานที่แนะนำ:

```
main
  └── feature/booking-flow
        └── commit เล็กและสื่อความหมาย
```

ตัวอย่าง Commit Message:

```
feat: add appointment booking API
test: cover duplicate booking validation
fix: prevent booking past time slots
docs: add project setup guide
```

Checklist ก่อน Commit:

- ดู `git diff` ทุกครั้ง
    
- ตรวจว่าไม่มีไฟล์ `.env` หรือ Secret
    
- รัน lint
    
- รัน test
    
- รัน build
    
- Commit เฉพาะไฟล์ที่เกี่ยวข้องกับงาน
    

Checklist สำหรับ Review งานจาก AI:

- โค้ดตรงตาม Spec หรือไม่
    
- มี edge case ที่ AI ลืมหรือไม่
    
- Error message เหมาะสมหรือไม่
    
- มีข้อมูลสำคัญหลุดใน log หรือไม่
    
- SQL query ปลอดภัยหรือไม่
    
- มี Test รองรับพฤติกรรมสำคัญหรือไม่
    
- มีการแก้ไฟล์นอกขอบเขตหรือไม่

# Module 12: Security Baseline — ป้องกัน Secret หลุด

ติดตั้งและใช้ `gitleaks` เพื่อตรวจหา Secret ที่หลุดใน repository

ตัวอย่างคำสั่ง:

```
gitleaks detect
```

สิ่งที่ต้องระวังเป็นพิเศษ:

- API Key
    
- Database URL
    
- Password
    
- Access token
    
- Private key
    
- LINE token
    
- AWS key
    
- ข้อมูลผู้ใช้หรือข้อมูลผู้ป่วย
    
- ไฟล์ `.env`
    

แนวทางที่ควรทำ:

- ใช้ `.env` และ `.env.example`
    
- เปิดใช้ secret scanning บน Git platform
    
- ใช้ pre-commit hook หากทีมพร้อม
    
- เปลี่ยน Key ทันทีเมื่อเผลอ Commit แม้ลบไฟล์ออกแล้ว
    
- จำกัดสิทธิ์ของ API key ให้เท่าที่จำเป็น
    

ข้อสำคัญ: หาก Secret หลุดขึ้น Git แล้ว การลบไฟล์อย่างเดียวไม่เพียงพอ ต้อง revoke หรือ rotate key นั้น

# Module 13: Definition of Done และการส่งมอบ

ก่อนบอกว่างานเสร็จ ต้องตอบให้ได้ว่า:

- ฟีเจอร์ทำงานตาม Acceptance Criteria หรือไม่
    
- มี Test สำหรับ logic สำคัญหรือไม่
    
- Lint, Test และ Build ผ่านหรือไม่
    
- ตรวจ Secret แล้วหรือไม่
    
- คู่มือใช้งานถูกอัปเดตหรือไม่
    
- ผู้ใช้งานทดลอง Flow หลักแล้วหรือไม่
    
- มีรายการสิ่งที่ยังไม่ทำหรือ Known Issues หรือไม่
    

รูปแบบรายงานส่งงาน:

```
## Delivered
- ผู้ใช้สร้างการจองได้
- ป้องกันการจองเวลาซ้ำ
- เจ้าหน้าที่ดูรายการจองได้

## Verified
- Lint ผ่าน
- Unit test ผ่าน
- Build ผ่าน
- ตรวจ gitleaks แล้วไม่พบ secret

## Remaining
- ยังไม่มีการแจ้งเตือนผ่าน LINE
- ยังไม่มีระบบยกเลิกการจอง
```
